# AGENTS.md

## Надстройка Excel `Аудиторам`
- Если задача касается корпоративной Excel-надстройки, вкладки `Аудиторам`, папок `addin/` или `addin_updater/`, сборки `AuditAddin.xlam` или обновления самой надстройки, обязательно сначала использовать отдельную инструкцию: `_publish/audit-macros-private/docs/addin-agent-instructions.md`.
- Если задача касается обычного updater-а макросов рабочих книг, который подтягивает `shared/*.bas` и `profiles/<profile>/*.bas`, а также его переключения между `Dev` и `Company/Work`, обязательно сначала использовать `_publish/audit-macros-private/docs/macro-updater-agent-instructions.md`.
- Если задача касается конструктора РД внутри надстройки, смешанного комплекта `Excel + Word`, шаблонов РД или генерации рабочих документов из файла `Анализ существенных статей`, после `addin-agent-instructions.md` использовать `_publish/audit-macros-private/docs/rd-constructor-agent-instructions.md`.
- Для задач по шаблонам РД на этой машине считать обязательной картой путей раздел `Зафиксированная карта путей` в `C:\Users\pavel\OneDrive\Рабочий стол\Шаблоны для конструктора\README.md`. Не искать похожие папки и не брать файлы из `Downloads` или recovery-архивов, если нужный путь уже зафиксирован там. Канонический dev-source каждого РД: `C:\Users\pavel\OneDrive\Рабочий стол\Шаблоны для конструктора\01_projects\<имя проекта>`; книга — в `template`, VBA — в `vba`, требования — в `contract`, входы — в `fixtures`, тесты и прогоны — в `tests`/`80_runs`. `01_workbooks` теперь только read-only generated publish input проектов со статусом `Ready`; вручную его не править и обратно из него не импортировать. Общие инструменты: `...\04_tools`; recovery: `...\99_archive`; старая плоская структура сохранена в `...\99_archive\workspace-v1-20260806-workspace-migration`. Пользовательские три артефакта: `C:\Users\pavel\OneDrive\Рабочий стол\Артефакты шаблонов РД\<имя шаблона>`; локальный company-release шаблонов РД `_publish\audit-macros-private\addin\release\rd-templates-company`; рабочий company-root `Z:\Project\DAVK\Оборудование\Addins`. `Z:` — только целевой путь на рабочих компьютерах; на этой машине его не искать, не монтировать и не менять.
- Для Excel/VBA E2E по шаблонам РД использовать локальный Excel на этой машине. Перед прогоном можно закрывать все `EXCEL.EXE`, затем запускать проверку через локальный Excel COM, локальные PowerShell-скрипты или подготовленную тестовую книгу. Тесты выполнять последовательно на этом компьютере; параллельные Excel-прогоны не запускать. На этой машине должна использоваться обычная рабочая структура `%APPDATA%\Microsoft\AddIns\AuditAddinLoader.xlam`, `%APPDATA%\AuditAddin\installed\AuditAddinLocal.xlam`, `%APPDATA%\AuditAddin\addin-updater.ini`, `%APPDATA%\AuditAddin\assets\Выборка`; для dev-прогонов в `AssetsRoot\Выборка` лежит общая dev-имитация модели и отбора. Тестовые макросы должны отключать лишние модальные окна (`DisplayAlerts=False`, явное закрытие книг, `RemovePersonalInformation=False` перед сохранением при необходимости, `CheckCompatibility=False`) и писать понятный итог/лог, а не ждать скрытый MsgBox или VBA error.
- Для dev-прогонов шаблонов РД выборку выполнять только через универсальные silent-сценарии надстройки `Аудиторам`: `AuditSampling_RunFullSilent`, `AuditSampling_RunModelFromSheetSilent`, `AuditSampling_RunSelectionFromSheetSilent`. Шаблоны не должны дергать UI-кнопки или несайлент-макросы модели/отбора, потому что мастер-сборка РД должна идти без лишних всплывающих окон. В dev эти silent-сценарии используют общую локальную имитацию модели и отбора из `AssetsRoot\Выборка`; в company-release те же silent-сценарии используют реальные корпоративные файлы модели и отбора из рабочего `AssetsRoot\Выборка`. Не создавать отдельные файлы модели/отбора и папки `_dev_sampling_<код шаблона>` под конкретный РД. По конкретному РД меняются только входные данные, числа, риски, правила подготовки популяции и количество групп `Модель_N`/`Отбор_N`, но не сам движок модели/отбора.
- Для задач по шаблонам РД последний проверенный company-release надстройки считать внешним источником правды и стабильным контрактом. Нельзя править `addin/`, `addin_updater/`, `AuditAddin.xlam`, loader/setup или логику `AuditSampling_*` только ради того, чтобы конкретный шаблон прошел тест. Если шаблон не совпадает с поведением надстройки, подстраивать шаблон, его входные листы, порядок активации листов и подготовку данных под уже работающую надстройку. Менять надстройку можно только по отдельной прямой задаче пользователя именно на надстройку.
- Для каждого шаблона РД отдельно согласовывать настройки на листе `Панель управления` в блоке `Настройки шаблона`: название, значения, дефолт, этап влияния и поведение при пустом значении. Не переносить настройки из `Е-130_Выручка` в другие РД автоматически; если непонятно, нужны ли `Отсекать ВГО`, `хвост ниже УОНИ`, `делить на 1000` или другие параметры, сначала спросить пользователя.
- Надстройка является отдельной функциональной линией, а не профилем. Для нее не применять правила `profiles/<profile>/` по умолчанию и не создавать `profiles/addin/`.
- Если задача касается переключения надстройки между `Dev` и `Company/Work`, использовать раздел `Как переключать режимы` из `_publish/audit-macros-private/docs/addin-agent-instructions.md` как основной runbook.
- Если меняются кнопки, меню или пользовательские сценарии вкладки `Аудиторам`, вместе с кодом обязательно обновлять встроенную инструкцию внутри надстройки.
- Если в надстройке появляется новая кнопка или новое крупное меню, для них обязательно находить или генерить подходящую по смыслу и стилю картинку и встраивать ее в Ribbon-пакет.

Каждый macro-enabled шаблон должен иметь собственный `modRdTemplateLogger` и не должен вызывать логгер запароленной надстройки.
- `addin_updater/tests/smoke-test.ps1` не считать частью обязательного цикла разработки надстройки. Гонять его только когда задача прямо затрагивает `addin_updater/` или company/work-механику доставки.
- Сборки и тесты вида `no-updater` и `diagnostic` считать obsolete-хвостами: не использовать, не восстанавливать и не развивать без прямого запроса пользователя.
- Локальный путь для company-релизов: `_publish/audit-macros-private/addin/release/company/`. При каждом новом company-release старые файлы переносить в `_publish/audit-macros-private/addin/release/company-archive/`, создавая подпапку с версией (например, `2026.04.19.092456/`). В самой папке `company/` хранить только актуальную сборку.

## Общие правила
- В начале каждой задачи, затрагивающей Git-репозиторий, фиксировать исходный `git status --short -uall` и отдельно учитывать уже существующие пользовательские изменения. Каждый созданный в задаче путь к завершению либо коммитить, либо удалять; нельзя оставлять новые untracked/ignored хвосты. Чужие незавершенные изменения не стадить и не удалять: при необходимости изолировать работу. Перед финальной передачей запускать корневой `tools/Assert-CleanWorktree.ps1`: он проверяет и этот workspace, и вложенный `_publish/audit-macros-private`. Завершенная задача должна оставить оба репозитория чистыми, если пользователь прямо не потребовал иного.
- Каждый новый диалог считать вне контекста прошлых обсуждений, если пользователь явно не сказал обратное.
- Не собирать контекст по проекту автоматически: не сканировать репозиторий, не читать историю Git и не изучать файлы без прямой необходимости.
- Работать только от текущего запроса пользователя.
- Если данных не хватает, задать один короткий уточняющий вопрос.
- Не придумывать новые архитектурные правила сверх зафиксированных ниже без согласования с пользователем.

## Репозиторий макросов
- Все `*.bas` хранить в репозитории `https://github.com/pashkarp14/audit-macros-private`.
- Ветку по умолчанию использовать `main`, если пользователь явно не указал другую.

## Структура репозитория
- `shared/*.bas` — общие модули
- `profiles/<profile>/*.bas` — профильные модули
- Никакие `manifest.json` не использовать.
- Updater автоматически подтягивает все `shared/*.bas`.
- Если в книге указан `Profile`, updater автоматически подтягивает все `profiles/<profile>/*.bas`.
- В `Profile` можно указывать несколько папок профилей через `,` или `;`.
- `shared/*.bas` и `profiles/<profile>/*.bas` поддерживать одной общей кодовой базой без отдельных dev/company-вариантов модулей: эти макросы все равно попадают в company-релиз, поэтому писать их сразу по company-ограничениям.
- Для company/work-режима обычного updater-а не использовать интернет и Git как источник обновления: макросы должны браться из согласованной сетевой папки через локальное зеркало `._macro_repo` по правилам из `macro-updater-agent-instructions.md`.
- Локальный путь для company-релизов обычных макросов: `_publish/audit-macros-private/macro_updater/release/company/`. При каждом новом company-release старые файлы переносить в `_publish/audit-macros-private/macro_updater/release/company/archive/`, создавая подпапку с версией (например, `archive/2026.04.20.101500/`). В самой папке `company/` хранить только актуальный пакет: `shared/`, `profiles/` и рабочую `*.xlsm`-книгу со встроенным updater-ом.
- У обычного updater-а поддерживать две runtime-версии:
  - `macro_updater/modMacroUpdater.bas` — dev runtime с Git-first логикой для разработки.
  - `macro_updater/modMacroUpdaterCompany.bas` — company runtime только для `Network/Local`, без Git/shell-кода.
- `*.xlsm` со встроенным company-updater-ом пересобирать только когда меняется сам updater runtime или стартовая книга. Если меняются только `shared/*.bas` и `profiles/<profile>/*.bas`, для уже выданной company-книги достаточно обновить содержимое сетевой папки.
- Пока ordinary `macro_updater` должен сам импортировать обновленные `shared/*.bas` и `profiles/<profile>/*.bas`, company `*.xlsm`-книга обязана оставаться без VBA-защиты. VBA-защиту для этой книги можно включать только для финального замороженного пакета, когда self-update больше не нужен, или после отдельной смены архитектуры.

## Обязательное уточнение перед созданием модуля
- Перед добавлением нового `*.bas` обязательно уточнять у пользователя, куда именно его класть:
  - в `shared/`
  - или в `profiles/<profile>/`
- Если пользователь явно не сказал, является ли модуль общим или профильным, не выбирать путь самостоятельно.
- Не создавать новые модули в `shared/` или `profiles/<profile>/` на основе догадки.
- Если неясно, к какому профилю относится модуль, сначала уточнить профиль у пользователя.

## Правила профилей
- Профиль определяется только именем папки в `profiles/<profile>/`.
- Если агент добавил, удалил или переименовал модуль в `profiles/<profile>/`, никаких дополнительных файлов синхронизации создавать не нужно.
- Для `shared/` и `profiles/` не создавать, не восстанавливать и не поддерживать `manifest.json`.
- Изменения в `shared/*.bas` и `profiles/<profile>/*.bas` синхронизируются только составом файлов в папках.

## Правила внесения изменений
- Общие модули класть только в `shared/`.
- Специфичные для документа или типа документа модули класть только в `profiles/<profile>/`.
- Не смешивать общую и профильную логику в одном модуле без явной необходимости.
- Новые профили создавать отдельной папкой `profiles/<profile>/`.
- Имена файлов `.bas` и имена модулей VBA держать согласованными.

## Правила кодировки VBA
- Исходные `.bas` можно хранить в репозитории как UTF-8, но VBE/Excel нельзя кормить такими файлами напрямую, если внутри есть русский или другой non-ASCII текст.
- Перед любым импортом `.bas` в VBE из PowerShell, smoke-теста, сборщика или разовой COM-проверки сначала создать временную ANSI-копию: прочитать исходник как UTF-8, записать временный файл через `Set-Content -Encoding Default`, импортировать временный файл, затем удалить временную папку.
- Не использовать прямой `$vbProject.VBComponents.Import($utf8BasPath)` для исходных `.bas` с русскими строками: MsgBox и тексты в ячейках превратятся в кракозябры.
- Если в Excel появилось окно с кракозябрами, сначала считать причиной неправильный импорт/кодировку теста или сборки, а не текст самого VBA-модуля.

## Правила общего логирования
- Общий модуль логирования хранить в `shared/modLogger.bas`.
- Логи писать только через публичные процедуры `modLogger`, а не прямой записью в лист `Логи`.
- В каждом пользовательском `Public Sub` или `Public Function`, который запускает сценарий, логировать старт через `Logger_StartRun`, ключевые этапы через `Logger_StartStep` и `Logger_EndStep`, завершение через `Logger_EndRun`, ошибки через `Logger_LogError`.
- `runId`, возвращённый `Logger_StartRun`, сохранять в локальной переменной процедуры и передавать во все вызовы логгера в рамках одного запуска.
- Для разовых сообщений между этапами использовать `Logger_Info`, `Logger_Warn`, `Logger_Error` или `Logger_Debug`.
- Поля `Module`, `Procedure` и `Stage` передавать явно и стабильно. `Stage` должен обозначать этап работы, например `LOAD_SOURCE`, `BUILD_REPORT`, `WRITE_OUTPUT`, `EH`.
- Лист `Логи` считать служебным. Не менять его структуру, заголовки и порядок колонок без явного запроса пользователя.
